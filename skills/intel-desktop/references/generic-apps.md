# Complete a task in an unfamiliar native app

The current model owns the user's requested result across tool calls. An
observation, a posted click, or a completed bounded transaction is one stage.
Compare the real app with the requested outcome; continue when another safe,
authorized stage can advance it. Generic apps may take longer than dedicated
chat adapters. Missing chat semantics, a new dialog, a transaction's step limit,
or one failed method does not finish the task.

## Observe, act, verify, continue

Start with `desktop_script(action:"list",app:...)` for a repeated app workflow.
A compatible verified/current-source parameterized plan can save discovery;
it still needs current parameters and actual postconditions. Otherwise use
`desktop_observe` or `desktop_inspect` for the authorized app. Keep the actual
user outcome in context, together with what has happened, what remains, and any
action whose result is unknown. Do not invent a new goal-tracking service.

Use AX roles, ancestry, menu paths, complete values and actual bounds first.
When AX is sparse or cannot explain the layout, obtain one current exact-window
`include_image:true` observation and combine its masked pixels/visual OCR with
the AX tree. `include_menus:true` adds the generic app's real native menu commands.
Check the returned image block and `image_available`, not only the requested flag.
An unavailable image preserves AX and its reason; use those available controls
or another supported observation rather than treating missing pixels as success
or immediately handing the task to the user. Truncated AX is partial context:
request a suitable current scope or larger bounded tree before claiming absence.

Generic window images are current-model context. Use generic `click`, `press`,
`key`, `type_text` or exact AX setters with their real target guards. Do not send
another app through the WeChat-only visual composer adapter. Coordinates come
from the actual target image and its pixel-to-point binding; observe again after
navigation. A screenshot is neither edit authorization nor proof of input success.

Choose one meaningful action or a short fixed-target batch/transaction. Several
mechanical actions with known controls can share one queue claim. Do not retain
the shared keyboard while thinking between model decisions. Use the normal
pre-claim signal and reaction interval; return saved focus at the end of each
foreground stage, including a known failure when its native guards allow return.
Retain one stable task ID across all stages. Do not restore over actual user
takeover, add a second lease, or leave the app foreground just to plan the next
step. The operation notice and capture release remain owned by the helper.

Read the resulting app state after each meaningful stage. When a native Open,
Save, sheet or remote-service dialog appears, follow the owner-published
`current_window` / `window_transition` to a fresh exact-title inspection under
the authorized app. Use the dialog's new IDs; the old document IDs and a matching
PID alone do not identify its controls. Close/finish the dialog through its
current controls, then inspect the resulting document/window again. Split
dynamic window changes into model-directed stages instead of forcing guessed
IDs or more than sixteen actions into one fixed-window plan.

`continuation.task_completion:"not_assessed"` says that the observation does not
decide whether the user's instruction is finished. Its `next_observation` is a
read-only suggestion; evaluate the user outcome before using it. A user request
only to inspect can finish after that read. For a longer instruction, keep
working until the actual requested document/value/navigation result is proved.
Never substitute `ok:true`, `events_posted`, candidate registration or a
successful intermediate check for that final result.

If an action fails, distinguish a known unexecuted step from unknown/partial
input. For unknown input, inspect the real current result first and preserve it;
never replay the old action automatically. Change an unsuccessful recognition
or navigation method using new AX/image/menu evidence. A genuine permission,
authorization, unavailable application capability or user-only business choice
can require the user; identify that exact dependency after completing the
independent safe work. Do not stop merely because the app has no special adapter.

## Collect and improve the demonstrated route

Register model-created application-control scripts, including failed probes,
with `desktop_script(action:"register",app,source_path,parameter_names,purpose)`.
The collector retains metadata and actual runtime evidence, never copied source,
invocation values, screenshots or credentials. Put variable business content in
parameters. Do not automatically execute a collected Python/Swift/shell file.

Convert the demonstrated safe stages to parameterized `desktop_plan/v1` plans
with fresh same-target, complete-value and focus postconditions. Store durable
sources in the runtime plans directory, register their actual paths/digests,
and verify through the installed plugin and real app. A moved or changed source
needs its own current evidence. Dynamic dialogue discovery can remain with the
model while proved mechanical stages become reusable. Prefer these stages on
the next compatible task; keep the model route available for changed layouts.

The authorized periodic maintenance consumes `daily_analysis.py analyze` and
`desktop_script(action:"analyze")`. Review the displayed conversion, repair,
verification and reuse entries, their current-digest evidence, failures and total
task/native timings. Select actual recurring problems, parameterize the observed
correction, and record real acceptance before favoring it. The report does not
run code, grant permission, create a scheduler or promote raw scripts. Source
and parameter changes invalidate old maturity; unknown actions never replay.

When the whole user instruction is verified, record its explicit same-task
preflight/stage/failure references with `desktop_task(action:"complete",...)`.
Report the real end-to-end span separately from native input latency and from
unmeasured earlier user/model time.
